# Database Design Document
## National Smart Energy Grid Intelligence & Demand Forecasting Platform

---

## Overview

This project uses **CSV files as a lightweight data store**, structured as if they were
database tables. This design choice was made to keep the project runnable without external
database infrastructure (see Deployment Guide, Section 6, for justification). The schema
below is written in standard table form and can be directly migrated to PostgreSQL/TimescaleDB
by creating matching tables and loading these CSVs via `COPY` or `pandas.to_sql()`.

---

## Table 1: `grid_demand_renewable` (grid_demand_renewable.csv)

Primary time-series table — one row per hour.

| Column | Type | Description |
|---|---|---|
| timestamp | DATETIME (Primary Key) | Hourly timestamp |
| hour | INTEGER | Hour of day (0–23) |
| day_of_week | INTEGER | 0=Monday ... 6=Sunday |
| month | INTEGER | 1–12 |
| is_weekend | BOOLEAN | 1 if Saturday/Sunday |
| residential_demand_mw | FLOAT | Residential electricity demand (MW) |
| industrial_demand_mw | FLOAT | Industrial electricity demand (MW) |
| total_demand_mw | FLOAT | Sum of residential + industrial demand |
| temperature_c | FLOAT | Ambient temperature (°C) |
| cloud_cover_pct | FLOAT | Cloud cover (0–100%) |
| wind_speed_mps | FLOAT | Wind speed (m/s) |
| solar_production_mw | FLOAT | Solar power generated (MW) |
| wind_production_mw | FLOAT | Wind power generated (MW) |
| battery_level_mwh | FLOAT | Battery storage level (MWh) |
| battery_level_pct | FLOAT | Battery storage level (% of capacity) |

## Table 2: `equipment_failures` (equipment_failures.csv)

Equipment/sensor readings table — used for failure prediction.

| Column | Type | Description |
|---|---|---|
| timestamp | DATETIME | Reading timestamp |
| equipment_id | VARCHAR (Foreign Key → equipment) | Transformer/equipment identifier |
| voltage_kv | FLOAT | Voltage reading (kV) |
| frequency_hz | FLOAT | Frequency reading (Hz) |
| load_pct | FLOAT | Load percentage on equipment |
| is_failure | BOOLEAN | 1 if a failure event occurred |
| failure_type | VARCHAR | transformer_failure / voltage_instability / frequency_deviation / equipment_overload / none |

**Relationship:** `equipment_id` links conceptually to a set of 50 simulated transformers
(`TRANSFORMER_001` to `TRANSFORMER_050`), representing substations across the grid.

---

## Table 3: Aggregated Load Tables (derived)

Generated by `data_processing.py` (Load Aggregation):

- `daily_load_aggregated.csv` — timestamp (day), total_demand_mw (daily sum)
- `weekly_load_aggregated.csv` — timestamp (week), total_demand_mw (weekly sum)
- `monthly_load_aggregated.csv` — timestamp (month), total_demand_mw (monthly sum)

These are analogous to **materialized views** in a relational database — pre-aggregated
rollups of Table 1 for faster reporting queries.

---

## Table 4: `grid_optimization_schedule` (grid_optimization_schedule.csv)

Output of the Linear Programming optimizer (`grid_optimization.py`).

| Column | Type | Description |
|---|---|---|
| hour | INTEGER | Hour of the optimized schedule |
| demand_mw | FLOAT | Demand at that hour |
| renewable_available_mw | FLOAT | Renewable supply available |
| grid_power_needed_mw | FLOAT | Grid power required to cover the gap |
| optimized_cost | FLOAT | LP-solved minimum distribution cost |

## Entity Relationship Summary

```
grid_demand_renewable (1) ---- (many) equipment_failures
       [linked by nearest timestamp]

equipment_failures (many) ---- (1) equipment_id
       [50 simulated transformers/substations]

grid_demand_renewable (1) ---- (1) grid_optimization_schedule
       [same timestamp, optimization output]
```

## Migration Path to Production Database

For a production deployment at true national-grid scale, this schema maps directly to:

- **PostgreSQL**: standard relational tables for `equipment` (static metadata)
- **TimescaleDB** (PostgreSQL extension): hypertables for `grid_demand_renewable` and
  `equipment_failures`, partitioned by `timestamp`, to handle the 15-million-smart-meter
  scale described in the case study with efficient time-series compression and querying
